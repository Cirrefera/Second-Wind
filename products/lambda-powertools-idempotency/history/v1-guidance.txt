WHEN THIS IS YOUR PROBLEM
Your handler moves money or writes downstream, and it runs on Lambda. Lambda
retries async invocations twice by default. SQS redelivers on visibility
timeout. EventBridge is at-least-once. Your handler WILL execute more than
once per logical event — the only question is whether the second execution
charges the customer again. This makes any handler idempotent in ~20 minutes.

STEP 1 — THE PERSISTENCE TABLE (one time)
The dedup state lives in DynamoDB. Create it exactly like this:

    aws dynamodb create-table \
      --table-name IdempotencyTable \
      --attribute-definitions AttributeName=id,AttributeType=S \
      --key-schema AttributeName=id,KeyType=HASH \
      --billing-mode PAY_PER_REQUEST

Then enable TTL so expired records clean themselves:

    aws dynamodb update-time-to-live --table-name IdempotencyTable \
      --time-to-live-specification Enabled=true,AttributeName=expiration

STEP 2 — IAM (the exact policy, nothing more)
Attach to the function role:

    { "Effect": "Allow",
      "Action": ["dynamodb:GetItem","dynamodb:PutItem",
                 "dynamodb:UpdateItem","dynamodb:DeleteItem"],
      "Resource": "arn:aws:dynamodb:*:YOUR_ACCOUNT:table/IdempotencyTable" }

STEP 3 — WIRE THE HANDLER

Python (pip install aws-lambda-powertools):

    from aws_lambda_powertools.utilities.idempotency import (
        idempotent, DynamoDBPersistenceLayer, IdempotencyConfig)

    persistence = DynamoDBPersistenceLayer(table_name="IdempotencyTable")
    config = IdempotencyConfig(
        event_key_jmespath="body.orderId",   # YOUR business key — see gotcha 1
        expires_after_seconds=3600,          # your real dedup window
    )

    @idempotent(persistence_store=persistence, config=config)
    def handler(event, context):
        return charge_customer(event)        # runs ONCE per orderId

TypeScript (npm i @aws-lambda-powertools/idempotency @aws-sdk/lib-dynamodb):

    import { makeIdempotent } from '@aws-lambda-powertools/idempotency';
    import { DynamoDBPersistenceLayer } from '@aws-lambda-powertools/idempotency/dynamodb';

    const persistenceStore = new DynamoDBPersistenceLayer({ tableName: 'IdempotencyTable' });
    export const handler = makeIdempotent(chargeCustomer, {
      persistenceStore,
      config: { eventKeyJmesPath: 'body.orderId', expiresAfterSeconds: 3600 },
    });

Java (software.amazon.lambda:powertools-idempotency-dynamodb):

    @Idempotent
    public Response handleRequest(Order order, Context ctx) { ... }
    // configure once at init:
    Idempotency.config()
      .withPersistenceStore(DynamoDBPersistenceStore.builder()
        .withTableName("IdempotencyTable").build())
      .withConfig(IdempotencyConfig.builder()
        .withEventKeyJMESPath("body.orderId")
        .withExpiration(Duration.ofHours(1)).build())
      .configure();

.NET (dotnet add package AWS.Lambda.Powertools.Idempotency):

    Idempotency.Configure(builder => builder
      .WithOptions(o => o.WithEventKeyJmesPath("Body.OrderId")
                         .WithExpiration(TimeSpan.FromHours(1)))
      .UseDynamoDb("IdempotencyTable"));

    [Idempotency]
    public Response Handler(Order order, ILambdaContext ctx) { ... }

THE GOTCHAS (each one is a production incident someone had)
1. Key on the BUSINESS id, never the Lambda request id. The request id
   changes on every retry — keying on it makes idempotency a no-op that
   looks like it works in testing.
2. The key must exist. If body.orderId can be absent, decide now:
   raise_on_no_idempotency_key=True (fail loud) or accept that keyless
   events execute unprotected. Silent default is the second one.
3. Return value is replayed, side effects are not un-done. The SECOND call
   gets the FIRST call's return value. If your handler already emailed the
   customer before failing, idempotency doesn't recall the email — put the
   side effect after the money move.
4. In-flight locking: a concurrent duplicate while the first is executing
   gets IdempotencyAlreadyInProgressError. That's correct behavior — map it
   to a 409/retry-later, don't swallow it.
5. expires_after_seconds is your dedup window, not a cache TTL. An event
   replayed AFTER expiry executes again. Match it to your upstream's maximum
   redelivery horizon (SQS: visibility timeout × maxReceiveCount).
6. The response is stored in the table — if the response contains PII/secrets
   you now have PII in DynamoDB. Either slim the return value or encrypt
   (payload_validation + KMS on the table).

VERIFY IT WORKS (2 minutes)
Invoke twice with the same orderId, different request ids:

    aws lambda invoke --function-name YourFn \
      --payload '{"body":{"orderId":"TEST-1","amount":100}}' /dev/stdout
    # run it again, identically

First call: your logic runs (check the charge happened once). Second call:
identical response, instantly, no side effects — and one item in
IdempotencyTable with your key hash. If the second call re-charged, you keyed
on the wrong path — see gotcha 1.
